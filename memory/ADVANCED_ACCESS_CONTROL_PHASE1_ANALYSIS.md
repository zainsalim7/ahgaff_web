## 2. البنية الحالية لنظام الصلاحيات (النظام القديم)
### 2.1 الأدوار
- **9 أدوار نظامية** في `models/permissions.py::UserRole`: admin, teacher, employee, student, dean, department_head, registrar, registration_manager, university_president.
- **أدوار مخصصة** تُنشأ عبر `/manage-roles` وتُخزَّن في collection باسم `roles` (حقل `is_system=False`)، وتُسنَد للمستخدم عبر `user.role_id`. يوجد حالياً 19 دوراً مخصصاً في القاعدة (منها 9 قوالب HR/إدارية جاهزة تُنشأ بزر واحد، والباقي أدوار أنشأها المستخدم فعلياً).
- **قيد حالي مهم**: المستخدم يملك دوراً واحداً فقط (`role` أو `role_id`) + حقل إضافي واحد `custom_permissions` (صلاحيات فردية إضافية، أُضيف في الجلسة السابقة). **لا يوجد مفهوم "تكليف متعدد" (Assignment) بتاريخ بداية/نهاية، ولا نطاق مستقل لكل دور عند تعدد الأدوار** — وهذا بالضبط ما يطلبه المشروع الجديد.

### 2.2 الصلاحيات
- 151 صلاحية مبرمجة، منها 138 ظاهرة للإدارة عبر `/manage-roles` و`/permissions`، و13 "مخفية" (تُمنح تلقائياً كجزء من صلاحية أشمل، مثل صلاحيات المحاضرات ضمن `manage_courses`).
- التحقق من الصلاحية: دالة `has_permission()` في `routes/deps.py` — الأدمن يمر دائماً، وبقية الأدوار تُفحص ضمن `permissions` الدور + `FULL_PERMISSION_MAPPING` (21 تجميعة "صلاحية شاملة تفتح صلاحيات فرعية تلقائياً").
- `custom_permissions` (مُضافة سابقاً): قائمة إضافية على المستخدم تُدمَج مع صلاحيات الدور دون المساس بالدور نفسه — هذا هو الأساس الوحيد الموجود حالياً لـ"الصلاحيات المباشرة/الاستثناءات" التي يطلبها المشروع الجديد، لكنه بلا نطاق (scope) مستقل ولا تاريخ انتهاء ولا سبب منح ولا جهة مانحة.

### 2.3 النطاقات (Scopes)
- **النطاق الأكاديمي**: حقول مباشرة على المستخدم (`faculty_id`, `department_id`, وأيضاً `faculty_ids[]`, `department_ids[]` الداعمة لتعدد محدود) + فلترة Faculty→Department المطبّقة عبر 12 شاشة (من الجلسة السابقة). لا يوجد مفهوم "برنامج أكاديمي" أو "مستوى" أو "شعبة" كنطاق صلاحية مستقل — هذه حقول بيانات على السجلات (مقرر/طالب) وليست كياناً للنطاق.
- **النطاق الإداري**: نظام `hr_scope` مستقل تماماً (`ALL` / `MY_UNIT` / `UNITS` + `hr_scope_unit_ids[]`) مبني فوق شجرة `org_units` (collection واحدة، 5 أنواع مبرمجة: `presidency`, `faculty`, `department`, `administration`, `office`) تُزامَن تلقائياً مع الكليات/الأقسام الأكاديمية. **هذه الشجرة مرنة بالفعل وتدعم إضافة وحدات مستقبلية دون تعديل كود** (مطلوب المستخدم رقم 8 محقق جزئياً في النظام القديم لنطاق HR فقط).
- **فجوة**: لا يوجد نوع "لجنة" أو "مجلس" صريح في `org_units` — الموجود الوحيد هو `faculty_board.py` (مجلس الكلية) كميزة مستقلة بمنطقها الخاص، وليس كنوع نطاق عام قابل لإسناد أي دور إليه.

### 2.4 الهيكل الأكاديمي/الإداري المكتشف فعلياً (Collections)

### 2.5 حجم السطح البرمجي (لماذا "كل زر" يعني عملاً ضخماً)
- 1016 واجهة API موزعة على 100+ ملف مسارات، تغطي: الطلاب، المعلمين، المقررات، الحضور، الدرجات، التقارير (15+ تقريراً فردياً)، المراسلات الرسمية (correspondence.py وحده 32 واجهة)، الجداول الأسبوعية (55 واجهة في ملف واحد)، شؤون الموظفين (hr*.py مجتمعة ~130 واجهة عبر 20 ملفاً)، الأرشيف، البطاقات، الشهادات، اللجان، إلخ.
- 1139 عنصر تحكم فريد في الواجهة (أزرار/حقول/نماذج)، منها ما لا يقل عن 196 عملية فعلية مباشرة (إضافة/تعديل/حذف/اعتماد/طباعة/تصدير/استيراد/نشر) تستحق صلاحية مستقلة وفق معيار المستخدم الصريح ("لا تُنشئ صلاحية لزر شكلي لا ينفذ عملية").
- هذا يعني أن **سجل الصلاحيات التفصيلي النهائي (Advanced Permission Registry) سيقع عملياً بين 250 و450 صلاحية مستقلة تقريباً** عند تطبيق معيار "عملية حقيقية فقط" بدقة على كامل الـ1016 واجهة، موزعة على ~25-30 مجموعة رئيسية (أقرب لقائمة المجموعات التي اقترحها المستخدم نفسه). الرقم النهائي الدقيق يُحدَّد فعلياً أثناء البناء في المرحلة 3 عند الفحص سطراً بسطر لكل Endpoint، وليس بالعدّ النظري وحده — هذا هو السبب في أن هذه الجولة اقتصرت على **البنية والمنهجية** بدل كتابة القائمة الكاملة فوراً دون تحقق من كل عملية.

## 3. الفجوات بين النظام القديم ومتطلبات المشروع الجديد
| المتطلب الجديد | الحالة في النظام القديم |
|---|---|
| تعدد الأدوار/المناصب لمستخدم واحد مع نطاق مستقل لكل منصب | **غير موجود** — دور واحد (`role_id`) + صلاحيات إضافية مسطّحة بلا نطاق مستقل |
| تكليف بتاريخ بداية/نهاية وحالة (نشط/منتهٍ) | **غير موجود** — لا تاريخ انتهاء لأي إسناد دور أو صلاحية |
| سياق عمل قابل للتبديل (Context Switching) | **غير موجود إطلاقاً** |
| نطاق مستقل بدقة (كلية واحدة/عدة كليات/مقررات مسندة...) لكل صلاحية على حدة | **جزئي** — موجود فقط كحقل عام على المستخدم (كل صلاحياته تتبع نفس `faculty_id`/`hr_scope`)، وليس لكل صلاحية نطاقها الخاص |
| سجل تدقيق مخصص لتغييرات الأدوار/الصلاحيات/التكليفات/النطاقات | **غير موجود كمنتج مستقل** — يوجد `activity_logs` عام غير مخصص لهذا الغرض |
| محاكي اختبار صلاحيات / مقارنة نظامين | **غير موجود** |
| لجان/مجالس كنوع نطاق عام قابل لإعادة الاستخدام | **غير موجود** — فقط ميزة مجلس كلية مخصصة |
| سجل صلاحيات شامل بمعرف فريد وربط مباشر بالـ API | **غير موجود بهذا المستوى من التفصيل** — القائمة الحالية (138) أشمل عملياً من دقة (عرض/إضافة/تعديل/حذف/اعتماد/طباعة/تصدير) لكل عملية فرعية |

## 4. البنية المقترحة لقاعدة البيانات الجديدة (تصميم فقط — لم تُنشأ بعد)
جداول مستقلة تماماً عن `roles`/`users.permissions`/`users.role_id` الحالية، بلا أي تعديل عليها:

1. **advanced_permissions** — السجل المركزي: `key` (فريد)، `label_ar`، `group_key`، `subgroup_key`، `operation_type` (view/add/edit/delete/approve/print/export/import/publish/bulk)، `sensitivity` (low/medium/high/critical)، `linked_api` (مسار الـ API الحقيقي)، `linked_page`، `scope_kind` (academic/administrative/mixed/none)، `is_active`.
2. **advanced_permission_groups** — المجموعات الرئيسية/الفرعية: `key`, `name_ar`, `parent_group_key`, `order`.
3. **advanced_roles** — أدوار النظام الجديد (منفصلة تماماً عن `roles` القديمة): `key`, `name_ar`, `description`, `permission_keys[]`, `status` (draft/shadow/ready_for_review), `imported_from_legacy_role_id` (مرجع اختياري فقط للنسخ المرجعي، بلا ربط حيّ).
4. **advanced_user_assignments** — صلب تعدد المناصب: `user_id`, `assignment_type` (academic/administrative), `advanced_role_key`, `context_label_ar` (مثال: "عميد كلية التعليم عن بعد")، `org_unit_id` أو `faculty_id`/`department_id` (حسب النوع)، `status` (active/suspended/ended)، `started_at`, `ended_at`.
5. **advanced_assignment_scopes** — نطاق مستقل لكل تكليف: `assignment_id`, `scope_type` (university/faculty/multi_faculty/department/multi_department/program/level/section/course/multi_course/assigned_courses/my_students/own_data/unit/multi_unit/committee/council)، `scope_ref_ids[]`.
6. **advanced_user_permissions** — الصلاحيات المباشرة/الاستثناءات لكل تكليف: `assignment_id`, `permission_key`, `scope_override` (اختياري)، `reason`, `granted_by`, `expires_at`.
7. **advanced_work_contexts** (سياقات العمل المتاحة فعلياً للمستخدم — تُشتق من `advanced_user_assignments` النشطة؛ قد تُحفظ كحالة Session فقط وليس جدولاً دائماً — يُحسم التصميم النهائي في المرحلة 2).
8. **advanced_permission_audit_logs** — مستقل عن `activity_logs` القديم: `actor_user_id`, `action` (role_created/role_updated/assignment_created/assignment_ended/permission_granted/permission_revoked/context_switched/test_access_granted)، `target_user_id`, `before`, `after`, `timestamp`.
9. **advanced_permission_test_results** — نتائج محاكي الاختبار (مرحلة لاحقة).
10. **advanced_access_testers** — قائمة المستخدمين المصرَّح لهم تجربة `/advanced-access-control` أثناء SHADOW (مستقلة عن `manage_users`/`manage_roles` القديمة تماماً): `user_id`, `sub_permissions[]` (دخول المركز / عرض / تبديل سياق / إدارة تجريبية / تعديل صلاحيات تجريبية / تشغيل اختبارات / عرض تقارير)، `granted_by`, `granted_at`, `revoked_at`.

جميع المعرّفات (`user_id`, `faculty_id`, `department_id`, `org_unit_id`) تُستخدم كما هي من المجموعات الحالية (`users`, `faculties`, `departments`, `org_units`) دون نسخها — قراءة فقط.

## 5. تصميم آلية تعدد المناصب وتبديل السياق (مقترح، لم يُبنَ بعد)
- كل سجل في `advanced_user_assignments` مستقل تماماً عن الآخر؛ حساب الصلاحية الفعّالة لأي عملية = `صلاحيات advanced_role المرتبط بالتكليف` + `advanced_user_permissions الخاصة بنفس التكليف فقط`، مقيَّدة بـ `advanced_assignment_scopes` **لنفس التكليف فقط** — لا تُدمَج صلاحيات/نطاقات تكليفين مختلفين أبداً (يحقق شرط المستخدم: تعديل بيانات طلاب كلية لا يمنح صلاحية كلية أخرى).
- "سياق العمل الحالي" = مجرد مؤشر (في الجلسة/التخزين المحلي للمتصفح) يختار أي `assignment` نشط يريد المستخدم رؤية مهامه وصلاحياته من خلاله داخل `/advanced-access-control` فقط. **لا علاقة له بالتوكن (JWT) الحقيقي ولا بأي قرار وصول فعلي في النظام القديم** — تماماً كما اشترط المستخدم.
- التحقق الأمني عند أي عملية تجريبية داخل الوحدة الجديدة: يُعاد حساب الصلاحية من قاعدة البيانات في كل مرة (لا يُعتمد على ما اختارته الواجهة فقط)، ويُرفض أي طلب لسياق لا يملك المستخدم تكليفاً نشطاً فيه.

## 6. آلية وضع SHADOW MODE (مقترح)
- حالات `advanced_roles`/النظام ككل: `DRAFT` → `SHADOW` → `READY_FOR_REVIEW` (لا توجد حالة `ACTIVE`/إنفاذ إنتاج ضمن هذا المشروع إطلاقاً، بنص صريح من المستخدم).
- كل واجهات API الجديدة تُسجَّل تحت بادئة مستقلة (مثال: `/api/advanced-access/*`) ولا تُستدعى من أي مسار قديم، ولا يُستدعى أي منطق جديد من داخل `has_permission()`/`require_permission()` الحاليين. وبذلك يستحيل بنيوياً أن يؤثر الكود الجديد على قرار وصول حقيقي — وليس فقط بشرط منطقي قابل للكسر.
- الوصول للوحدة الجديدة بالكامل (صفحة + API): حارس مستقل يتحقق من (الأدمن) **أو** (وجود سجل نشط في `advanced_access_testers` لنفس المستخدم) — منفصل تماماً عن `manage_users`/`manage_roles` القديمة.

## 7. المخاطر والضمانات
| الخطر | الضمانة المقترحة |
|---|---|
| تسرّب تأثير على النظام القديم | جداول جديدة بالكامل + بادئة API منفصلة + عدم استدعاء أي دالة قديمة للكتابة؛ قراءة فقط من `users/faculties/departments/org_units` |
| تضخم عدد الصلاحيات (250-450) يصعّب الإدارة | تجميع هرمي صارم (مجموعة رئيسية → فرعية) + بحث فوري + علم `hidden` للصلاحيات شديدة التخصص كما في النظام القديم |
| غياب نوع "لجنة/مجلس" عام | إضافة النوعين كقيم جديدة في `scope_type` بجدول `advanced_assignment_scopes` الجديد فقط (لا تعديل `org_units` القديم) |
| تعقيد حساب الصلاحية الفعلية عبر تكليفات متعددة | عزل صارم لكل تكليف (قسم 5 أعلاه) + اختبارات تلقائية مخصصة لهذا السيناريو تحديداً في المرحلة 2 |
| نسيان تحديث سجل الصلاحيات عند إضافة ميزة جديدة مستقبلاً | `linked_api`/`linked_page` إلزاميان لكل صلاحية + تقرير "نسبة تغطية" دوري (مطلوب أصلاً في تقرير المرحلة النهائية) |

## 8. خطة التنفيذ المحدَّثة (بعد موافقتك على هذا التقرير)
- **الجولة القادمة (الجولة 2 — بعد موافقتك الصريحة)**: إنشاء الجداول العشرة أعلاه + بناء سجل الصلاحيات الفعلي (فحص كل واجهة من الـ1016 فعلياً لتحديد العدد النهائي الدقيق 250-450) + خدمات الباك إند الكاملة لحساب الصلاحية الفعّالة/النطاق/تعدد المناصب/تبديل السياق + استيراد نسخة مرجعية من الأدوار الـ28 الحالية كبيانات ابتدائية فقط + اختبارات باك إند فعلية (pytest) تغطي كل سيناريوهات القسم 19 من طلبك المتعلقة بالبنية الخلفية.
- **لن يبدأ في الجولة القادمة**: الواجهة الإدارية، المحاكي، صفحة المقارنة — هذه تنتظر موافقتك الصريحة بعد تسليم تقرير الجولة 2.
- **لم يُنفَّذ أي تغيير برمجي حتى هذه اللحظة** — هذا الملف تحليل فقط.

## 9. ما لم يُغطَّ بعد (شفافية)
- لم تُفحص بعد كل واجهة من الـ1016 واحدة تلو الأخرى لاستخراج اسمها العربي الدقيق وصلاحيتها المقترحة الفردية (هذا عمل المرحلة 2/3 الفعلي، كما أوضحتُ في القسم 2.5) — ما قُدِّم هنا هو حصر كمّي دقيق + منهجية التصنيف، وليس القائمة التفصيلية الكاملة لكل الـ250-450 صلاحية، تفادياً لتسليم قائمة شكلية غير محقَّقة فعلياً بحق كل زر كما شدّدتَ.
- عدد المستخدمين/الكليات/الأقسام الحالي (16/2/4) هو بيانات بيئة الاختبار الحالية وليس بالضرورة بيانات الإنتاج الفعلية.
