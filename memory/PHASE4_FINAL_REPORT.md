# التقرير النهائي — المرحلة 4: الاختبار التشغيلي الشامل والتحقق من جاهزية مركز الصلاحيات المتقدم
تاريخ: 29 أكتوبر 2026 | الوضع طوال المرحلة: SHADOW MODE بالكامل — لا اعتماد ولا ترقية لأي دور.

## 1) تمييز جوهري: اختبار البنية vs اختبار السلوك الأمني الحقيقي
هذا التمييز مطلوب صراحة وهو الأساس لفهم ما تعنيه "النجاح" في كل قسم أدناه:

- **اختبار بنيوي (Structural)**: يتحقق أن السجل في قاعدة البيانات *صحيح ومطابق للكود الحقيقي* (الصلاحية موجودة، مرتبطة بدالة/مسار API حقيقي فعلاً في الكود). **لا يثبت أي حماية فعلية** — لأنه لا يستدعي الـ API الحقيقي ولا يختبر رفض/سماح فعلي.
- **اختبار سلوكي/أمني (Behavioral/Security)**: يستدعي فعليًا منطق الحساب (`check_permission`, `compare`) أو واجهة المستخدم الحقيقية، ويتحقق من قرار سماح/رفض حقيقي، بما في ذلك محاولات اختراق فعلية (انتحال، تصعيد، تجاوز نطاق، IDOR).
- **حقيقة مهمة يجب توضيحها للمستخدم**: مركز الصلاحيات المتقدم بكامله هو SHADOW MODE — أي أن كل هذه القرارات (سماح/رفض) هي *قرارات داخلية في النظام التجريبي نفسه فقط*. لا يوجد أي مسار API حقيقي في النظام القديم يتحقق حاليًا من هذه الصلاحيات الجديدة أو يُقيَّد بها. لذلك "اختبار سلوكي ناجح" هنا يعني "منطق العزل والحساب داخل النظام الجديد يعمل بشكل صحيح ومتسق"، وليس "تم تأمين واجهات API الحقيقية للجامعة بهذه الصلاحيات" — ذلك لن يحدث إلا عند قرار اعتماد مستقبلي صريح من المستخدم (غير حاصل الآن).

## 3) اختبار مجموعات الصلاحيات الثلاثين (فردي/جماعي/حفظ/تعديل/إلغاء)
اختُبر فعليًا (API + واجهة):
- اختيار صلاحية واحدة فردية عند إنشاء دور — نجح.
- اختيار مجموعة كاملة دفعة واحدة (bulk/select-all) — نجح، تحقَّق عدد الصلاحيات المحفوظة مطابق تمامًا.
- تعديل دور موجود: إضافة صلاحيات ثم إزالتها — نجح، التغييرات تُحفظ فعليًا (ليست مجرد واجهة).
- تجربة فعلية عبر الواجهة من `testing_agent`: مجموعة "الحضور" (34 صلاحية) → تحديد فردي +1 = 35 → تعديل: حذف 1 (34) ثم إضافة 2 (36) — كل الأرقام طابقت.

## 4) تعدد المناصب المستقل لنفس المستخدم
اختُبر مستخدم واحد (Saeed) بثلاثة تكليفات متزامنة:
1. أكاديمي (عميد كلية تجريبي) — نطاق كلية محددة.
2. إداري (مسؤول إداري تجريبي) — نطاق الجامعة بالكامل.
3. إداري آخر (مسؤول وحدة تجريبي) — نطاق وحدة إدارية محددة.

**النتيجة المؤكدة**: كل تكليف يرى صلاحيته الخاصة فقط ولا يرى صلاحيات التكليفَين الآخرَين لنفس المستخدم إطلاقًا — عزل كامل ومؤكَّد عبر `check_permission` وعبر قراءة تفاصيل كل سياق (`/assignments/{id}/context`) بشكل منفصل. تأكيد مطابق عبر الواجهة (AdvContextPage + المبدّل العالمي) أيضًا.

## 5) تبديل سياق العمل من كل الصفحات
- الزر العالمي (الأرجواني، أعلى يمين الشاشة) ظهر وعمل فعليًا من 3 صفحات مختلفة من النظام القديم (`/`, `/students`, `/manage-roles`) بالإضافة لصفحة المركز نفسه.
- تأكيد صريح: **القائمة الجانبية ونصوصها وصلاحيات النظام القديم الفعلية بقيت مطابقة تمامًا قبل وبعد تبديل السياق** — التبديل للعرض فقط، لا يغيّر أي قرار حقيقي.
- قيد معروف وموثَّق (غير مُصلَح، منخفض الخطورة): السياق النشط يُفقد عند تحديث الصفحة (متوقَّع لأنه حالة عرض مؤقتة وليس توكن حقيقي)، ولا يُبطَل تلقائيًا فور إنهاء تكليفه (يبقى حتى تبديل يدوي تالٍ).

## 6) الوحدات الإدارية والأكاديمية — الاكتشاف التلقائي
أُنشئت وحدة إدارية تجريبية مباشرة في قاعدة البيانات (محاكاة لإضافة وحدة جديدة من النظام القديم) ثم استُدعي `GET /scope-options/unit` **بلا أي إعادة فحص يدوي أو تحديث للسجل** — ظهرت فورًا في قائمة الخيارات. نفس المبدأ يسري على الكليات/الأقسام (تُقرأ مباشرة من مجموعات النظام القديم، لا نسخة مخزَّنة تحتاج تزامنًا يدويًا).

## 7) انتهاء التكليفات
اختُبر إنهاء تكليف واحد من أصل تكليفين نشطين لنفس المستخدم:
- التكليف المُنهى: فورًا يُرفض أي فحص صلاحية عليه بسبب "غير نشط".
- التكليف الآخر لنفس المستخدم: **بقي نشطًا وسليمًا تمامًا، لم يتأثر إطلاقًا.**
تأكيد مطابق عبر الواجهة (AdvAssignmentsManager): القائمة تعكس الحالة الصحيحة فورًا.

## 8) الاختبارات الأمنية الموسّعة
| الاختبار | الأداة | النتيجة |

| تصعيد صلاحيات ذاتي (إسناد دور الأدمن المستورد للنفس) | pytest + تأكيد واجهة (رسالة الخطأ ظهرت فعليًا للمستخدم) | **مرفوض (403)** |

| تعديل دور مستورد من النظام القديم من غير الأدمن | pytest + تأكيد واجهة | **مرفوض (403)** |

| عزل الجلسات بين المستخدمين (admin ← logout ← Salim بلا إعادة تحميل) | screenshot فعلي | **لا تسرّب** — الزر العالمي يختفي فورًا |

## 9) مراجعة الثغرتين من المرحلة 3 — هل عولجتا من الجذر؟
- **IDOR**: نعم من الجذر. الإصلاح في طبقة الـ API نفسها (`GET /assignments/{id}/context`) يتحقق من الملكية الفعلية أو صلاحية `run_tests`، وليس إخفاءً في الواجهة فقط. تم التحقق مجددًا بمختبر جديد له `context_switch` فقط (بدون `run_tests`) — ما زال محجوبًا.
- **تصعيد الصلاحيات**: عولج جزئيًا من الجذر في المرحلة 3 (منع الإسناد للنفس)، واكتشف `testing_agent` في هذه المرحلة أن نفس الثغرة كانت لا تزال قائمة بصيغة أخرى (إسناد الدور المستورد *لمستخدم آخر*). تم الآن إغلاق المسارَين معًا: لا يمكن لغير الأدمن إسناد أي دور مستورد من النظام القديم (`imported_from_legacy_role_id`) — سواء لنفسه أو لغيره.

## 10) المحاكي ومقارنة النظامين
- المحاكي: نتائج منطقية ومتسقة — سماح داخل النطاق، رفض خارجه مع سبب واضح، رفض عند غياب الصلاحية من الدور.
- المقارنة: تصنيف `both_allow` / `both_deny` / `no_legacy_equivalent` صحيح، ومجموع التصنيفات يطابق عدد الصلاحيات الفعّالة القابلة للمقارنة تمامًا (تحقّق رياضي آلي).
- ⚠️ "المقارنة" تقرأ فقط — لا تُغيّر أي قرار حقيقي في النظام القديم، وهذا مؤكَّد.

## 11) اختبار الواجهة (كمبيوتر وجوال، RTL)
نُفِّذ عبر `testing_agent` على 1920×800 (كمبيوتر) و390×844 (جوال):
- كل التبويبات الـ11 تعمل بلا كسر، على الجهازين.
- النصوص العربية واتجاه RTL سليم بعد الإصلاحات (كان هناك ترتيب LTR خاطئ في قوائم الاختيار الأفقية — أُصلح).
- **أخطاء اكتُشفت وأُصلحت في هذه الجولة**:
  1. تبويب "المختبرون" كان يطرد أي مختبر غير أدمن من المركز بالكامل (403 على نداء إداري حصري) — أُصلح بعدم استدعائه إلا للأدمن.
  2. لوحة المعلومات كانت تعرض كل الأرقام صفرًا للمختبرين غير الأدمن بسبب فشل أحد النداءات الإدارية ضمن `Promise.all` — أُصلح باستخدام `Promise.allSettled` وتخطي النداءات الحصرية للأدمن.
  3. تراكب الأزرار العائمة (القائمة/البحث/مبدّل السياق) مع عنوان صفحة المركز وزر الرجوع — أُصلح بزيادة المساحة العلوية للهيدر.
  4. عدة نداءات بلا معالجة أخطاء كانت تُنتج شاشة حمراء عند أي 403 — أُضيفت معالجة أخطاء شاملة.
  5. بحث المحاكي كان يطابق الاسم العربي فقط — أُضيف البحث بالمفتاح والمسار، وعُرض المسار تحت كل خيار لتمييز الصلاحيات متشابهة الاسم.
